# Медиагалерея с CMS и асинхронной обработкой видео

## 1. Описание проекта

Микросервис медиагалереи предоставляет REST API для загрузки, хранения и отдачи медиаконтента (JPEG, PNG, MP4), а также динамического контентного модуля (CMS) для управления блоками страниц.

Ключевые возможности:

- загрузка изображений и видео с валидацией типа и размера;
- асинхронная конвертация MP4 в HLS (мастер-плейлист `.m3u8` и сегменты `.ts`) с помощью `ffmpeg`;
- гибридное хранение: метаданные и статусы — в PostgreSQL, бинарные файлы и HLS-потоки — на локальном диске;
- CMS-блоки с гибкой JSONB-структурой и привязкой медиафайлов по схеме «многие ко многим»;
- автоматические миграции БД при старте сервиса;
- полная контейнеризация через Docker Compose.

Технологический стек:

| Компонент       | Технология                              |
|-----------------|------------------------------------------|
| Язык            | Go 1.26                                  |
| СУБД            | PostgreSQL 16                            |
| Контейнеризация | Docker, Docker Compose                   |
| Миграции        | golang-migrate                           |
| Конфигурация    | godotenv, 12-Factor App                  |
| Обработка видео | ffmpeg, ffprobe                          |
| API             | REST, Go 1.22+ `http.NewServeMux`        |

## 2. Архитектура

Проект следует принципам Clean Architecture. Зависимости направлены от внешних слоёв к внутренним.

### Структура слоёв

```
cmd/
api/          — точка входа HTTP API
worker/       — точка входа фонового обработчика видео
internal/
domain/       — доменные сущности, интерфейсы портов, типы статусов
usecase/      — бизнес-логика загрузки, обработки и CMS
infrastructure/
config/         — загрузка ENV-конфигурации
persistence/    — PostgreSQL-репозитории
storage/        — локальное файловое хранилище
worker/         — ffmpeg-видеопроцессор
delivery/http/  — REST-обработчики, DTO, роутер
pkg/
logger/      — структурированное логирование на базе log/slog
```

Доменный слой не знает о HTTP, SQL или ffmpeg. Взаимодействие с БД, файловой системой и процессами ffmpeg выполняется через интерфейсы-порты (`MediaRepository`, `JobQueue`, `VideoProcessor`, `FileStorage`).

### Асинхронный пайплайн обработки видео

1. Пользователь загружает MP4 через `POST /api/media/upload`.
2. Файл валидируется, сохраняется на диск, метаданные записываются в `media_assets`.
3. В той же транзакции создаётся запись в очереди `processing_jobs` со статусом `queued`.
4. Фоновый worker периодически запрашивает следующую задачу через `Claim`.
5. Для выборки задачи используется `SELECT ... FOR UPDATE SKIP LOCKED`, что гарантирует: одну задачу не возьмут несколько worker-реплик.
6. Worker запускает `ffprobe` для получения метаданных, затем `ffmpeg` для конвертации в HLS.
7. HLS генерируется во временной директории, после успешного завершения — атомарно перемещается в финальную `storage/hls/{asset_id}/`.
8. `media_assets.hls_path` обновляется, статус меняется на `ready`.

### CMS и связи многие-ко-многим

Таблица `content_blocks` хранит:

- `id` — UUID блока;
- `page_key` — ключ страницы;
- `block_type` — тип блока (`text`, `carousel`, `reviews`, `about`);
- `data` — JSONB-контент блока;
- `sort_order` — порядок сортировки.

Связь с медиафайлами вынесена в `content_block_media_links`:

```
content_blocks 1 ──── * content_block_media_links * ──── 1 media_assets
```

Это позволяет одному блоку ссылаться на несколько медиафайлов и одному медиафайлу участвовать в нескольких блоках.

## 3. Инструкция по быстрому запуску

### Требования

- Docker
- Docker Compose v2

### Запуск

```bash
docker compose up --build
```

После запуска:

- PostgreSQL поднимается на порту `5432`;
- HTTP API доступен на порту `8080`;
- worker автоматически подключается к очереди задач;
- миграции БД применяются автоматически при старте API.

Проверить готовность сервиса:

```bash
curl http://localhost:8080/healthz
```

Ответ:

```
ok
```

## 4. Сценарий демонстрации (Definition of Done)

Для e2e-проверки используется коллекция Postman:

```
docs/media-gallery.postman_collection.json
```

### Шаг 1. Health Check

Выполнить `GET /healthz`.

Ожидание: HTTP `200 OK`, тело `ok`.

### Шаг 2. Загрузка изображения или видео

Выполнить `POST /api/media/upload` с полем `file` в `multipart/form-data`.

Допустимые форматы:

- изображения: JPEG, PNG;
- видео: MP4.

При загрузке изображения статус сразу `ready`.  
При загрузке видео — `queued`, создаётся задача обработки.

Ожидание: HTTP `202 Accepted`, в ответе:

```json
{
  "id": "<media-asset-id>",
  "status": "queued"
}
```

### Шаг 3. Ожидание готовности видео

Для проверки статуса можно использовать `GET /api/media/{id}` (если эндпоинт включён в актуальную версию API) или проверить появление файла `master.m3u8` в хранилище.

Worker автоматически заберёт задачу, выполнит ffmpeg и обновит статус на `ready`.

### Шаг 4. Создание CMS-блока

Выполнить `POST /api/cms/blocks` с JSON:

```json
{
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "page_key": "home",
  "block_type": "carousel",
  "data": {
    "title": "Welcome to our gallery",
    "subtitle": "Featured works"
  },
  "sort_order": 1,
  "media_ids": [
    "<media-asset-id-1>",
    "<media-asset-id-2>"
  ]
}
```

Ожидание: HTTP `200 OK`, создаётся блок и связи с указанными медиафайлами.

### Шаг 5. Получение CMS-блока

Выполнить `GET /api/cms/blocks/a1b2c3d4-e5f6-7890-abcd-ef1234567890`.

Ожидание: HTTP `200 OK`, в ответе блок с массивом `media`, содержащим метаданные привязанных файлов:

```json
{
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "page_key": "home",
  "block_type": "carousel",
  "data": {
    "title": "Welcome to our gallery",
    "subtitle": "Featured works"
  },
  "sort_order": 1,
  "media_ids": ["<media-asset-id-1>", "<media-asset-id-2>"],
  "media": [
    {
      "id": "<media-asset-id-1>",
      "original_file_name": "photo.jpg",
      "media_type": "image/jpeg",
      "status": "ready"
    }
  ]
}
```

## 5. Технический долг и ограничения MVP

На текущем этапе зафиксированы следующие ограничения и направления развития.

### Ограничения MVP

- файлы хранятся на локальном диске, нет горизонтального масштабирования хранилища;
- API не имеет JWT/OAuth-авторизации, доступ ограничен на уровне инфраструктуры;
- worker обрабатывает задачи с фиксированным интервалом опроса очереди;
- HLS генерируется в одном качестве (single rendition);
- нет дедупликации загруженных файлов по контенту;
- нет версионирования CMS-блоков и отката изменений;
- отсутствует полноценный CI/CD с e2e-тестами и нагрузочным тестированием.

### План будущих спринтов

1. **Миграция файлового хранилища в S3**  
   Реализовать `FileStorage` для S3/MinIO. Сохранить текущий интерфейс, добавить стратегию «локально / объектное хранилище».

2. **Авторизация и аутентификация**  
   Внедрить JWT-токены, роли, rate limiting, API keys с scopes.

3. **Улучшение обработки видео**
    - несколько renditions (1080p, 720p, 480p);
    - прогресс обработки в реальном времени;
    - отмена задачи;
    - метрики `ffmpeg` (CPU, память, время транскодирования).

4. **CI/CD и качество кода**
    - e2e-тесты в Docker Compose;
    - контрактные тесты API;
    - гонки и нагрузочное тестирование;
    - покрытие кода unit-тестами ≥ 80%.

5. **Наблюдаемость**
    - экспорт метрик в Prometheus;
    - трассировка запросов через OpenTelemetry;
    - сбор логов в централизованное хранилище.

6. **Управление очередью**  
   Рассмотреть переход с PostgreSQL-очереди на Redis Streams или RabbitMQ при росте нагрузки.

Документация поддерживается в актуальном состоянии. Коллекция Postman — в `docs/media-gallery.postman_collection.json`.  
Миграции — в `internal/infrastructure/persistence/postgres/migrations/`.
