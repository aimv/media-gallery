# ADR-0001: Использование PostgreSQL SKIP LOCKED в качестве очереди задач

*   **Статус:** Принято
*   **Дата:** 2026-08-23
*   **Контекст:** см. `docs/1_ANALYSIS.md`

## Context

В рамках MVP микросервиса медиагалереи требуется асинхронная обработка видео (конвертация MP4 в HLS). После загрузки видео создаётся задача, которая должна быть обработана фоновым воркером. В перспективе возможен запуск нескольких воркеров для горизонтального масштабирования.

Необходимо выбрать механизм очереди задач, который:
- Обеспечивает надёжную доставку задач без потерь при сбоях.
- Гарантирует, что одна задача не будет обработана двумя воркерами одновременно.
- Минимизирует количество дополнительной инфраструктуры в Docker Compose.
- Соответствует принципам Clean Architecture (абстракция через порт).
- Подходит для ожидаемой нагрузки MVP (до сотен задач в день).

Рассматривались следующие альтернативы:
1. **RabbitMQ** – полноценный брокер сообщений.
2. **Apache Kafka** – распределённый лог.
3. **PostgreSQL с SKIP LOCKED** – использование БД как очереди.

## Decision

Принято решение использовать **PostgreSQL с механизмом `FOR UPDATE SKIP LOCKED`** в качестве очереди задач для MVP. Таблица `processing_jobs` играет роль очереди. Воркеры выполняют атомарный `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)` для получения следующей задачи.

Для поддержки отказоустойчивости реализован механизм lease (аренды):
- Каждая взятая задача получает `lease_owner` (идентификатор воркера) и `lease_expires_at`.
- Воркер периодически обновляет lease (heartbeat).
- Если lease истекает (воркер упал или завис), другой воркер может перехватить задачу после обнуления lease.

Очередь имеет ограниченную семантику: повторная обработка возможна через механизм attempt и requeue. Гарантируется идемпотентность обработки (см. Analysis, раздел 5.2).

## Consequences

### Положительные

- **Простота инфраструктуры**: в Docker Compose требуется только один дополнительный сервис `postgres`, который уже используется для хранения метаданных. Нет необходимости разворачивать RabbitMQ или Kafka.
- **Снижение операционных затрат**: меньше сервисов для мониторинга, меньше точек отказа.
- **Транзакционная согласованность**: задачи и метаданные хранятся в одной БД, что упрощает атомарные операции (например, вставка задачи при создании медиафайла может быть в одной транзакции).
- **Достаточная производительность для MVP**: при правильных индексах и умеренном количестве задач (сотни/тысячи в день) SKIP LOCKED работает надёжно.
- **Отсутствие vendor lock-in**: интерфейс `JobQueue` в domain-слое изолирует реализацию; в будущем можно заменить на RabbitMQ/Kafka без изменения бизнес-логики.

### Отрицательные

- **Ограниченная масштабируемость**: при очень высокой нагрузке (десятки тысяч задач в секунду) PostgreSQL может стать узким местом. Для MVP это приемлемо.
- **Меньше возможностей по сравнению с брокерами**: нет встроенной маршрутизации, ретраев с backoff, dead-letter queue — всё нужно реализовывать самостоятельно (что частично сделано через таблицу `processing_jobs`).
- **Риск блокировок**: длинные транзакции или неправильные запросы могут вызвать конфликты блокировок. Требуется аккуратное проектирование запросов и индексов.
- **Управление lease вручную**: необходимо строго следить за обновлением lease и обрабатывать случаи истечения, что добавляет сложности в воркере.

### Нейтральные

- **Зависимость от PostgreSQL**: система уже зависит от PostgreSQL для хранения данных, поэтому дополнительная зависимость не вносит нового риска.
- **Паттерн "Database as Queue"** известен и широко применяется, но требует дисциплины в проектировании схемы.

## Compliance

Соответствие критериям из Analysis:
- Атомарный claim задачи через `FOR UPDATE SKIP LOCKED` ✔️
- Lease expiration и heartbeat ✔️
- Идемпотентность обработки ✔️
- Минимизация инфраструктуры ✔️

## Notes

Для перехода на внешнюю очередь в будущем необходимо:
1. Сохранить интерфейс `JobQueue` без изменений.
2. Создать новую реализацию интерфейса (например, `RabbitMQQueue`).
3. Добавить миграцию данных из `processing_jobs` в новую очередь (при необходимости).

Дополнительные детали реализации очереди см. в `docs/2_DESIGN.md`, раздел 4.2.
