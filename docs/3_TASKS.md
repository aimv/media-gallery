**Файл:** `docs/3_TASKS.md`  
**Статус:** План реализации утвержден  
**Роль:** Агент-Скрам-мастер / Техлид  
**Методология:** Итеративная разработка (микро-задачи 1–2 часа)

---

## 1. Общие правила декомпозиции

- Каждая задача — атомарный шаг, который можно выполнить за 1–2 часа и проверить независимо.
- Задачи выполняются последовательно внутри спринта; спринты — последовательно.
- После каждой задачи создается коммит с осмысленным сообщением.
- Критерий проверки (Definition of Done) описан для каждой задачи.
- Если задача занимает более 2 часов — она разбивается дополнительно.

## Спринт 1: Инфраструктурный скелет

**Цель:** Создать базовую структуру проекта, конфигурацию и логгер, чтобы все последующие слои имели фундамент.

### T1.1 Инициализация Go-модуля и структуры папок

- Создать `go.mod` с именем модуля `github.com/yourorg/media-gallery`.
- Создать структуру папок согласно `docs/2_DESIGN.md`: `cmd/`, `internal/domain/`, `internal/usecase/`, `internal/infrastructure/`, `internal/pkg/`, `docs/`.
- Создать `.gitignore` для Go, Docker, `.env`, `tmp/`, `hls/`, `originals/`.
- Создать `Makefile` с командами: `build`, `run-api`, `run-worker`, `test`, `lint`, `migrate-up`, `migrate-down`.

**Критерий:**  
`go build ./...` выполняется без ошибок. Структура папок соответствует дизайну. `make help` выводит список команд.

---

### T1.2 Загрузка конфигурации из ENV

- Создать `internal/infrastructure/config/config.go`.
- Определить структуру `Config` с полями: `HTTPPort`, `DBDSN`, `StorageRoot`, `WorkerCount`, `LeaseDuration`, `MaxUploadSizeMB`, `APIKey`, `FFmpegPath`, `FFprobePath`.
- Реализовать функцию `Load() (*Config, error)`, читающую переменные окружения с дефолтными значениями.
- Создать `.env.example` с документированными переменными.

**Критерий:**  
`Load()` возвращает корректные значения из `.env`. При отсутствии обязательной `DBDSN` возвращается ошибка.

---

### T1.3 Инициализация структурированного логгера

- Создать `internal/pkg/logger/logger.go`.
- Обернуть `log/slog` в кастомный логгер с уровнями: `Debug`, `Info`, `Warn`, `Error`.
- Добавить middleware для присвоения `request_id` каждому запросу и прокидывания его в контекст.
- Логировать в JSON-формате для продакшена.

**Критерий:**  
Логгер инициализируется из `main.go`. При выполнении HTTP-запроса в логе присутствует `request_id`. Уровень логирования управляется через ENV.

---

### T1.4 Скелетные точки входа API и Worker

- Создать `cmd/api/main.go`, который загружает конфиг, инициализирует логгер и запускает заглушечный HTTP-сервер с `/healthz`.
- Создать `cmd/worker/main.go`, который загружает конфиг, инициализирует логгер и выводит `worker started` (заглушка).
- Настроить graceful shutdown через `signal.NotifyContext`.

**Критерий:**  
`go run ./cmd/api` запускает сервер на порту из конфига, `GET /healthz` возвращает `200 OK`. `go run ./cmd/worker` выводит `worker started` и корректно завершается по `SIGTERM`.

## Спринт 3: Модуль загрузки и FileStorage

**Цель:** Реализовать загрузку файлов, их сохранение на диск и метаданные в БД.

### T3.1 Реализация локального `FileStorage`

- Создать `internal/infrastructure/filestorage/local/storage.go`.
- Реализовать интерфейс `FileStorage`:
    - `Save` — копирование потока в файл по пути;
    - `Delete` — удаление файла/директории;
    - `Open` — чтение файла;
    - `Move` — атомарное перемещение файла/директории.
- Создавать промежуточные директории автоматически.
- Защита от path traversal: путь строится только из UUID.

**Критерий:**  
Unit-тесты на `Save`/`Delete`/`Move` с временной директорией проходят. Попытка `Open("../../etc/passwd")` возвращает ошибку.

---

### T3.2 Use Case загрузки медиафайла

- Создать `internal/usecase/media/upload.go`.
- Реализовать функцию `UploadMedia(ctx, input UploadInput) (*MediaAsset, error)`:

- Для изображений статус сразу `ready`.

**Критерий:**  
Unit-тест с мок-репозиториями: при успешной загрузке изображения статус `ready`, при ошибке БД файл удаляется. Для видео создается job со статусом `queued`.

## Спринт 4: Асинхронный воркер и интеграция с ffmpeg

**Цель:** Реализовать фоновую обработку видео, управление ffmpeg-процессами и конкурентный claim задач.

### T4.1 Реализация `VideoProcessor` через ffmpeg/ffprobe

- Создать `internal/infrastructure/video/ffmpeg/processor.go`.
- Реализовать метод `Probe(ctx, filePath)` через `exec.CommandContext(ctx, ffprobePath, ...)`.
- Реализовать метод `ConvertToHLS(ctx, inputPath, outputDir)` через `ffmpeg` с аргументами для HLS:
    - `-hls_time 4`
    - `-hls_list_size 0`
    - `-hls_segment_filename`
    - `-preset veryfast`
    - `-progress pipe:1`
- Использовать `Setpgid` и `CommandContext` с таймаутом.
- Возвращать ошибку при ненулевом exit code.

**Критерий:**  
Ручной запуск `ConvertToHLS` на тестовом MP4 создает `master.m3u8` и `.ts`-сегменты. При отмене контекста процесс убивается (проверка через `ps`).

---

### T4.2 Реализация воркера-раннера

- Создать `internal/infrastructure/worker/runner.go`.
- Реализовать цикл:
    1. `Claim` задачи из очереди;
    2. запуск обработки в горутине с ограничением `WorkerCount`;
    3. логирование и обработка паники;
    4. `Heartbeat` каждые `LeaseDuration/3`.
- Запускать несколько воркеров (по умолчанию 1).

**Критерий:**  
Воркер запускается и логирует получение задач. При пустой очереди — ожидание через `time.Sleep` (или `pgx` listen).

---

### T4.3 Use Case обработки видео

- Создать `internal/usecase/media/process.go`.
- Реализовать `ProcessVideo(ctx, jobID)`:
    - загрузить job и asset по `job.AssetID`;
    - проверить статус `queued` или `processing` (идемпотентность);
    - установить статус `processing`;
    - запустить `VideoProcessor.Probe`;
    - запустить `VideoProcessor.ConvertToHLS` во временную директорию;
    - атомарно переместить HLS в финальную `hls/{assetID}/`;
    - обновить `asset.hls_path` и статус `ready`;
    - пометить job `done`.
- При ошибке: пометить job `failed`, увеличить `attempt`, при попытках < max — вернуть в `queued`.

**Критерий:**  
Unit-тест с mock `VideoProcessor`: после успешной обработки asset.status = `ready`, job.status = `done`. При ошибке — корректный retry.

---

### T4.4 Обработка lease и повторных попыток

- Реализовать в раннере проверку `lease_expires_at` перед обработкой.
- Если lease истек и статус `processing`, разрешить повторный claim.
- Реализовать `Heartbeat` с обработкой ошибок.
- Настроить max attempts и backoff.

**Критерий:**  
Интеграционный тест: если воркер падает после claim, задача через lease-таймаут снова становится доступной для другого воркера.

---

### T4.5 Graceful shutdown и управление ffmpeg

- В `cmd/worker/main.go` использовать `signal.NotifyContext`.
- При получении сигнала:
    - прекратить claim новых задач;
    - дождаться завершения текущих (с таймаутом);
    - отменить контексты запущенных ffmpeg;
    - корректно закрыть пул соединений.

**Критерий:**  
При `SIGTERM` воркер завершает текущую задачу не более чем за заданный таймаут. Все ffmpeg-процессы убиты, нет zombie-процессов.

---

### T4.6 Dockerfile и запуск воркера в Compose

- Создать `Dockerfile.api` и `Dockerfile.worker` на базе `golang:1.22-alpine`.
- Собрать бинарники, добавить ffmpeg и ffprobe в образы (или использовать `linuxserver/ffmpeg` как базовый).
- Обновить `docker-compose.yml`: добавить сервисы `api` и `worker`, зависящие от `postgres`.
- Продублировать volume для хранения `originals/` и `hls/`.

**Критерий:**  
`docker compose up --build` поднимает все сервисы. Загрузка MP4 через API инициирует обработку воркером в контейнере. HLS-файлы появляются на volume.

---

### T4.7 E2E-тест обработки видео

- Подготовить тестовый MP4-файл (1–2 секунды, малый размер).
- Написать интеграционный тест (или скрипт) полного цикла:
    - загрузка через API;

    - проверка наличия `master.m3u8` и `.ts`;

**Критерий:**  
Тест проходит автоматически. Время выполнения теста < 10 секунд. Файлы корректны и HLS проигрывается.
